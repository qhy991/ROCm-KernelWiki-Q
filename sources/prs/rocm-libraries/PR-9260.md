# Slab-Granularity K LDS Padding for gfx950 Attention

## Landing Status

PR #9260 merged on 2026-07-10 into the feature branch
`users/avirgoel/ck/d256-gfx950-opt`, not the repository's `develop` branch.
That feature branch entered `develop` through PR #9233 on 2026-07-22. PR #9233
explicitly describes its shipped measurements as including the K-LDS slab
padding from #9260.

## Summary

The usual "add one element to every LDS row" rule is not universally safe.
This gfx950 attention path loads two-row K slabs with asynchronous DMA, so
row-level padding would break the contiguous transfer layout.

The PR inserts padding between the two-row slabs instead. The QK read mapping
uses the same slab stride, preserving producer/consumer agreement while
shifting successive slabs away from the conflicting bank pattern.

## Source-Reported Performance

For MI355X/gfx950 D256 BF16 prefill at sequence length 8192, using an FP32
reference, the PR reports:

| Metric | Before | After |
|---|---:|---:|
| Latency | 1592 us | 1195 us |
| Bank-conflict events per 1000 | 897 | 660 |
| Relative to PyTorch FlashAttention | 0.86x | 1.14x |

The source reports roughly a `4.5x` reduction in bank-conflict cycles and about
25% lower latency. Numerical maximum absolute error is reported as `0.015625`.
LDS use remains around 65 KB with two workgroups per CU, and VGPR use is
unchanged.

PR #9260 does not state the complete head/batch workload in its body. Its
`develop` landing PR, #9233, identifies the shipped cohort as GQA 16/2, causal,
batch 1, D256 BF16 prefill. That later attribution should not be mistaken for
metadata reported directly by #9260.

## Reusable Lesson

Padding belongs at the granularity of the conflicting access pattern and must
respect the transfer primitive. For asynchronous multi-row copies, first
preserve the contiguous DMA slab, then pad between slabs and update the read
mapping consistently.

## Scope and Limits

The reported measurements are for gfx950 D256 attention. The layout principle
is reusable, but the exact padding and performance result are not portable
constants. The 2026-07-10 merge date records the feature-branch merge; the
upstream `develop` landing date is 2026-07-22.
