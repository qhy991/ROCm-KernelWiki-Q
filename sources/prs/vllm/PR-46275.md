# Split Sparse MLA Decode on gfx942

## Summary

vLLM's DeepSeek-V4 sparse MLA decode already had a split Triton path on
gfx950. This PR extends the architecture guard to gfx942 so MI300X uses a
partial kernel followed by a reduction kernel instead of the monolithic
ragged-decode fallback.

The implementation change is intentionally small: it extends the tuned
architecture guard so gfx942 selects the existing split path. The PR reports
the measured result but does not isolate a compute-unit-level causal mechanism.

## Source-Reported Kernel Results

The PR benchmarks production-style DeepSeek-V4 cache packing with
`MAIN_LEN=80` and `EXTRA_LEN=32`:

| Queries | Ragged fallback | Split partial + reduce | Improvement |
|---:|---:|---:|---:|
| 1 | 42.754 us | 22.836 us | 46.59% |
| 8 | 42.260 us | 23.088 us | 45.37% |
| 32 | 42.547 us | 24.490 us | 42.44% |
| 128 | 43.463 us | 34.121 us | 21.49% |

A high-throughput profiler run reports sparse-decode time decreasing from
`2542.147 ms` to `1535.915 ms`, a 39.58% reduction. Serving-level gains are
smaller: warm high-throughput output throughput is effectively at parity,
while the low-rate decode-heavy workload reports about 4.5% lower warm TPOT.

## Correctness and Serving Evidence

- 41 ROCm sparse-attention tests passed on gfx942.
- Maximum absolute difference in the kernel benchmark was at most `2.44e-4`.
- An 8x MI300X DeepSeek-V4-Flash smoke request returned the same answer.
- GSM8K limit-20 flexible and strict exact-match scores remained `0.95`.

The upstream environment used a vLLM ROCm nightly image, tensor parallel size
8, FP8 E4M3 KV cache, and AITER enabled.

## Changed Files

- `vllm/v1/attention/ops/rocm_aiter_mla_sparse.py`
- `tests/kernels/attention/test_rocm_triton_attn_dsv4.py`

## Scope and Limits

This is a gfx942 dispatch enablement for an existing kernel pair, not a new
general sparse-attention algorithm. Kernel time improves substantially, but
end-to-end serving impact depends on request rate and the fraction of runtime
spent in sparse decode.
